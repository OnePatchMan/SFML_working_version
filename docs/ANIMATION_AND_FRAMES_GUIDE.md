# Руководство по кадрам (Frame Data), анимациям и рисованию спрайтов

Данный документ содержит полное техническое описание работы кадров, боевой анимации, таймингов из `combat_balance.kv`, правил создания спрайт-листов, а также детальный архитектурный анализ поведения физики и анимации при различной частоте кадров (60, 144, 240 FPS).

---

## 1. Анатомия боевого удара (Fighting Game Frame Data)

В профессиональных 2D-файтингах (Street Fighter, Guilty Gear, Mortal Kombat) золотым стандартом измерения времени является **1 игровой кадр при 60 FPS**:

$$\text{1 кадр (Frame)} = \frac{1}{60} \text{ секунды} \approx 0.01667 \text{ с} \approx 16.67 \text{ миллисекунд}$$

Любой боевой прием состоит из трех последовательных фаз:

```
[ Нажатие кнопки ]
       │
       ▼
┌──────────────────┐   ┌────────────────────────┐   ┌────────────────────────┐
│     STARTUP      │ ─►│         ACTIVE         │ ─►│        RECOVERY        │
│  (Замах / Кадры  │   │  (Активные кадры удара │   │    (Восстановление /   │
│   подготовки)    │   │   и включения хитбокса)│   │   возврат в стойку)    │
└──────────────────┘   └────────────────────────┘   └────────────────────────┘
```

### 1.1. Фаза 1: Startup (Подготовка / Замах)
* **Что происходит**: От момента нажатия клавиши атаки до первого кадра, на котором наносится урон.
* **Зачем нужно художнику**: В этот момент персонаж замахивается рукой, отводит назад булаву или приседает перед ударом ногой (Anticipation).
* **Почему в KV-таблице не было параметра `startup`?**
  * В текущей программной логике для максимальной мгновенной отзывчивости («snappy response») удары генерировали хитбокс сразу на 1-м кадре после нажатия кнопки ($\text{Startup} \approx 0\dots 1$ кадр).
  * Для качественной плавной анимации **рекомендуется выделять 1–3 кадра замаха** (например, быстрый джеб — 1–2 кадра замаха $\approx 0.03\text{с}$, тяжелый удар булавой — 4–6 кадров $\approx 0.08\text{с}$).

### 1.2. Фаза 2: Active (Активные кадры / Удар)
* **Что происходит**: Окно времени, когда хитбокс существует в мире и может поразить врага.
* **В файле `combat_balance.kv`**: Параметр `active_time` (задан в секундах).
* **Формула перевода в кадры @ 60 FPS**:
  $$\text{Кадры} = \text{round}(\text{active\_time} \times 60)$$
  * Например, для базового джеба `active_time = "0.11"` $\rightarrow 0.11 \times 60 \approx 6.6 \approx \mathbf{7 \text{ кадров}}$.

### 1.3. Фаза 3: Recovery (Восстановление / Follow-through)
* **Что происходит**: Оружие уже пролетело, хитбокс выключился, персонаж возвращается в нейтральную боевую стойку (Idle). В этот момент игрок уязвим к контратаке.
* **В файле `combat_balance.kv`**:
  * `player_recovery` — длительность восстановления, если удар **попал** во врага или блок.
  * `whiff_stun` — увеличенное время уязвимости, если игрок **промахнулся** по воздуху.
* **Формула перевода в кадры @ 60 FPS**:
  $$\text{Кадры Recovery} = \text{round}(\text{player\_recovery} \times 60)$$
  * Например, `player_recovery = "0.14"` $\rightarrow 0.14 \times 60 \approx \mathbf{8\text{ кадров}}$.

## 3. Практическое руководство: как рисовать спрайты для игры

### 3.1. Технические спецификации спрайтов
1. **Размер одного кадра**:
   * Базовый хитбокс персонажа: $32 \times 32$ пикселя.
   * Для персонажа с оружием или длинными шлейфами (VFX/Smear) рекомендуемый холст кадра: $48 \times 48$ или $64 \times 64$ пикселя.
2. **Формат спрайт-листа**:
   * Горизонтальная полоса (Horizontal Strip PNG): все кадры располагаются в один ряд слева направо.
   * Например, если анимация состоит из 6 кадров размером $48 \times 48$, то размер PNG-файла будет:
     $$\text{Ширина} = 6 \times 48 = 288\text{ px}, \quad \text{Высота} = 48\text{ px}$$
3. **Ориентация спрайта**:
   * **ВАЖНО**: Исходный спрайт в файле должен быть нарисован лицом **ВЛЕВО (Facing Left)**!
   * Движок игры при повороте персонажа вправо применяет программное зеркалирование по горизонтали `sprite.setScale(-1.0f, 1.0f)`.
4. **Точка привязки (Origin / Pivot)**:
   * Ноги персонажа должны упираться в нижнюю линию тайла.
   * Рекомендуемый Pivot: геометрический центр ног по горизонтали, подошва по вертикали: $(\text{Width} / 2, \text{Height})$.

### 3.2. Принцип файтинг-анимации (Ключевые позы)
Чтобы анимация выглядела мощной и динамичной («weighty impact»), не нужно рисовать каждый из 60 кадров секунды! В файтингах используется **метод ключевых поз**:

```
Кадр 1: Стойка/Подготовка (Idle/Wind-up)  -> держится 1-2 тика
Кадр 2: Пик замаха (Anticipation)        -> держится 1 тик
Кадр 3: Удар со смазом (Smear / Impact)   -> держится 2 тика (момент урона)
Кадр 4: Фиксация в точке удара (Hold)    -> держится 2 тика
Кадр 5: Откат назад (Follow-through)     -> держится 2 тика
Кадр 6: Возврат в нейтрал (Recovery)     -> держится 2 тика
```

* **Smear Frame (Кадр-смаз)**: Кадр с белым или цветным динамическим росчерком (шлейфом) оружия или кулака передает иллюзию бешеной скорости удара без необходимости отрисовывать десятки промежуточных кадров.

## 4. Архитектурный разбор: Влияет ли разный FPS на геймплей и анимации?

В текущей версии движка используется переменный шаг времени:
```cpp
float dt = dtClock.restart().asSeconds();
if (dt > 0.1f) dt = 0.1f; // Clamp от скачков при лагах
```

### 4.1. Влияние на анимации (`Animator.cpp`)
* **Проблема отсутствует!** Класс `Animator` использует реальное абсолютное время таймера SFML:
  ```cpp
  if (_clock.getElapsedTime().asSeconds() >= _frameTime) {
      _currentFrame++;
      _clock.restart();
  }
  ```
* Это гарантирует, что при установленном времени кадра `frameTime = 0.05f` (20 кадров в секунду для спрайта) анимация будет идти **с абсолютно одинаковой визуальной скоростью** и на 60 FPS, и на 144 FPS, и на 240 FPS.

### 4.2. Влияние на физику и прыжки (Численное интегрирование Эйлера)
* **Текущее поведение**:
  ```cpp
  velocity.y += gravity * dt;
  position += velocity * dt;
  ```
  При явном интегрировании Эйлера при разной частоте кадров накапливается незначительная погрешность:
  * При **60 FPS** шаг времени $dt \approx 0.0166\text{ с}$ (60 итераций в секунду).
  * При **240 FPS** шаг времени $dt \approx 0.00416\text{ с}$ (240 итераций в секунду).
* **Практический эффект**: Разница в пике прыжка составляет менее $1\dots 2$ пикселей на экране, что практически незаметно глазу, однако для строгого киберспортивного детерминизма (например, покадровых сетевых откатов Rollback Netcode) правильным подходом является **Fixed Timestep Accumulator**.

### 4.3. Рекомендуемый стандарт для киберспортивного детерминизма (Fixed Timestep)
Если в будущем потребуется 100% математическая идентичность каждого кадра физики независимо от частоты развертки монитора, в главном цикле применяется классический паттерн накопителя:

```cpp
const float FIXED_DT = 1.0f / 60.0f; // Строго 60 тиков физики в секунду
float accumulator = 0.0f;

while (window.isOpen()) {
    float frameTime = dtClock.restart().asSeconds();
    if (frameTime > 0.25f) frameTime = 0.25f;
    accumulator += frameTime;

    while (accumulator >= FIXED_DT) {
        player.update(FIXED_DT, arena);
        combat.update(FIXED_DT, ...);
        accumulator -= FIXED_DT;
    }

    // Рендеринг выполняется так быстро, как позволяет монитор (uncapped / 144 / 240 fps)
    window.clear();
    // draw(...)
    window.display();
}
```

## 5. Итоги и рекомендации для художников

1. **Сколько кадров рисовать для каждой атаки?**
   * Быстрые джебы и тычки (`1`, `f1`, `b1`, `dw1`): **4–5 кадров** в спрайт-листе.
   * Средние удары и удары в воздухе (`2`, `a1`, `a2`, `d1`): **6 кадров** в спрайт-листе.
   * Тяжелые финишеры и броски (`u2`, `adw2`, `1-2-f1`, `b2-1-u2`): **7–8 кадров** в спрайт-листе.
2. **Скорость показа кадров в игре**:
   * При экспорте спрайт-листа в движок устанавливайте параметр `frame_duration = 0.03f - 0.04f` секунды на кадр. Тогда анимация из 5 кадров завершится ровно за $0.15\dots 0.20$ секунды, идеально совпав с окном активности и восстановления из `combat_balance.kv`.
3. **Хитбоксы и обратная связь**:
   * Добавляйте эффект удара (Flash / Smear) именно на 2-й или 3-й кадр анимации — именно в этот момент враг получит урон и брызнет кровь.
